# Architecture

How the code is organized, where the boundaries are, and how to extend it without breaking the structure. Behavior lives in docs/UX-SPEC.md; visual rules in docs/DESIGN-SYSTEM.md.

## Shape

```
bigsmall/
├── packages/core        @bigsmall/core — the engine. Pure TypeScript. Zero runtime deps. No DOM.
└── apps/web             @bigsmall/web  — the site. Astro shell, Preact islands (React API), Tailwind over tokens.
```

Two packages, one direction of dependency: `web` imports `core`, never the reverse. The pnpm workspace makes this a physical boundary, `packages/core/tsconfig.json` has no DOM library, and ESLint forbids framework and DOM imports inside core and internal-path imports from web (ADR 0003).

Per keystroke the converter's state parses the box's text (`parse`: the number or arithmetic, and the unit query after it) and builds the table (`selectTable`): while a unit is typed, `search` ranks units and categories across every category, the current one preferred (`prefer`), so it wins ties without hiding the others; otherwise `search('')` lists the category's units in their order, and `convert` and `formatNumber` give each row its value. `resolveExact` (whether a query names exactly one unit) decides the unit typed before an ingredient in Cooking (`2 cups flour`), and `unitListGroup` ranks a unit's section where the converter arranges a list; `suggest` (parse and search in one call) stays in core's API, tested, though the converter no longer calls it (ADR 0013). All pure functions over the registry; nothing is cached across calls because the registry is small.

Unit kinds:

- **linear**: `base = value × factor`. Almost everything.
- **affine**: `base = (value + offset) × factor`. Temperature scales.
- **reciprocal**: `base = factor ÷ value`, both ways. Fuel per distance against distance per fuel (L/100 km, gal/100 mi), and pace against speed (min/km, min/mi), whose units carry `pace: true`: written in minutes and seconds (`formatClock`), listed after the rest (`orderUnits`), and in a Pace section of their own on the web.
- **functional**: custom `toBase` / `fromBase`, for a relation no factor can say: the children's shoe scales, ISO 19407's Table 3 with straight lines between its rows, carried on past the ends so the function is total, with a `range` the web's rows say Out of range beyond (ADR 0027).

A unit marked in steps (`step`: a shoe scale's half size) is written to its step by the web's rows, ≈ where that moved it (`roundToStep`, rounded.ts); one written before its number carries `prefix`; one agreed by a body rather than defined carries `conventional` (ADR 0027).

Every conversion is `from → base → to`. Nothing chains through a third unit, so error never accumulates beyond two floating-point operations.

### Islands and the inline script

Astro renders every page to static HTML. JavaScript ships for components marked `client:*` and for an Astro component's own `<script>` (the wordmark's), and only islands carry the framework: Preact, with `preact/compat` answering the components' `'react'` imports (ADR 0007). A TSX component used without a directive (the icons inside Astro components) renders to plain markup. Rule of thumb: if a thing can be HTML plus a few lines of inline script, it is not an island. The header menus are the worked example: ThemePicker and ShortcutsHelp are Astro markup driven by one controller in the inline script of `Base.astro` (its attributes are in docs/DESIGN-SYSTEM.md, "Fluid shells"), so they work before any bundle loads and add none (ADR 0002, outcome note). The page's toolbars and planes are driven from the same script (ADR 0014).

### Theming

A theme is a set of CSS custom properties on `[data-theme="id"]`. Components consume semantic tokens through Tailwind utilities (`bg-canvas`, `text-ink`, `rounded-md`) that resolve to those properties at runtime, so switching themes touches one attribute on `<html>`. Details in [DESIGN-SYSTEM.md](DESIGN-SYSTEM.md) and [THEMING.md](THEMING.md).

### State and URLs

The converter state lives in the island and serializes to the URL (format in docs/UX-SPEC.md §11). Preferences live in `localStorage`: the theme, and the settings (`bigsmall:settings`, Display stored by what was changed, versioned, `settings-store.ts`); `/dev/wordmark-lab` and `/dev/sketchbook-lab` keep their settings there too. There is no server state (ADR 0001).

- Anything the user edits in the converter, the calculator's entry included, lives in the reducer's state and its one history; panels are views of that state, so undo always takes back the last thing done, wherever it was done. Settings aside: they are preferences, kept out of the history and the URL (ADR 0018).
- Behavior that depends on timing takes the time in the action (`at`) and decides in the reducer: the component only reports when things happened, and tests pass explicit times rather than faking timers.

## Build and runtime

- `pnpm dev` runs the Astro dev server; `pnpm build` writes a static site to `apps/web/dist`; `pnpm preview` serves that build.
- Core ships as TypeScript source (`exports` points at `src/index.ts`); Vite compiles it with the app. No build step for core.
- `scripts/bundle-size.mjs` measures what the converter page ships, gzipped; `pnpm bundle:check` enforces the budgets (docs/PLAN.md §9). It prints the data fetched on demand, the brands' charts, beside the budget and outside it (ADR 0029).
- `scripts/seo-check.mjs` holds every page in the built sitemap to the SEO contract, and every page left out of it to `noindex` (`pnpm seo:check`, docs/SEO.md §1).
- Hosting is Vercel, with `bigsmall.work` as the main domain (ADR 0008). The Vercel project is `apps/web` with its Astro preset, and `apps/web/vercel.json` adds the headers; setup, releases, and rollbacks are in docs/DEPLOYMENT.md. The build is a static site, so any static host can serve it.
- A few kilobytes of code load with the page and run nothing until needed (the wordmark's motion). `import()` is only for code far larger than the preload helper Vite wraps it in (about 0.8 KB gzipped), and a new chunk must show up in `pnpm bundle`.

## Conventions

- File names: kebab-case for `.ts`/`.css` modules, PascalCase for TSX and Astro components.
- Imports: from `@bigsmall/core` only; relative paths inside a package.
- No default exports in TypeScript modules. Astro components and tool config files (`astro.config.mjs`, `eslint.config.js`, `playwright.config.ts`, `playwright.preview.config.ts`, `vitest.config.ts`) are the exceptions, by framework design.
- Comments explain why, not what. Decisions go in `docs/decisions/`, surprises in `docs/LEARNINGS.md`.
- In an Astro file, notes go in the frontmatter as a block comment, or in `{/* */}` inside the template. An HTML comment ships in every built page, and `test/astro-templates.test.ts` fails on one.
- Islands are written against the React API and run on Preact through `preact/compat`. The compat differences that shape code (layout effects for work that must happen before the next key, DOM names for boolean attributes that can be `false`, `event.currentTarget`, a first client render equal to the server's) are in ADR 0007, "Consequences".
- A component that hands `className` to `cx()` types it as a plain string (`Omit<…, 'className'>` plus `className?: string`), as `Button` does, since preact/compat's typing also allows a signal there. The deprecation hints `astro check` prints for compat's React type names are expected.
- Typed text is read with the visitor's separators (`NumberEnv`). A web function that parses it takes them as a required argument (`stateToParams(state, separators)`), so no caller falls back to the defaults by forgetting. The reducer's own `parse()` calls only ask whether there is a number, where it ends, and whether text follows it, which the separators do not change.
- Around a change that moves focused elements in the page (a reorder, a list swapped), note `document.activeElement` before it and focus it again in a layout effect after, if it lost focus: a browser drops focus from whatever it moves (docs/LEARNINGS.md, "Moving an element drops the focus inside it"; `SystemRows`). Moving focus to a field another render creates waits for that render the same way.
- A type or an interface is exported only where another file reads it; a component's `Props` interface stays local unless a caller needs it (`CheckboxProps`, read by `TriCheckbox`), so an export is a reader's claim, never a habit (the tidy of 2026-10-18).
- A special character gets a named constant, built once with `String.fromCharCode` (`MINUS` and `NBSP` in core's `format.ts` and `parse.ts`, which the calculator and the table import; `DIGIT_GROUP` in the wordmark's), never a Unicode escape in source, and regexes are built from those constants.
